- 새 시스템을 만들거나, 기존 시스템을 개선하기 위해 현재 사용중인 업무 방식, 프로그램, 데이터, 서버, 네트워크, 문제점을 조사하고 정리하는 활동

- 새로운 시스템을 정확하게 만들기 위해 현재 상황을 이해한다.

문제점

1. 기존 업무의 흐름을 모른다면 필요한 기능을 빠트릴 수 있다.
2. 기존 데이터 구조를 모른다면 데이터 이전 시 오류 발생
3. 기존 시스템 연동을 모른다면 외부 시스템과 연결 실패
4. 사용자 불편 사항을 모른다면 새 시스템을 만들어도 만족도가 낮다.
5. 현재 원인을 모른다면 문제 해결이 아닌 단순 재개발이 된다.

요구사항 관리 툴
요구사항 문서를 엑셀이나 한글 파일로만 관리하지 않고, 변경 이력, 승인 상태, 담당자, 추적 관계까지 체계적으로 관리하는 도구

요구사항 관리툴을 사용하는 이유

- 요구사항은 프로젝트 중간에 계속 바뀐다.
누가 바꿨는가
언제 바꿨는가

승인되었는가

테스트도 바뀌어야 하는가
위와 같은 내용을 관리해야 한다.

사람이 파일로 관리하면 빠트리기 쉽기 때문에 요구사항 관리툴을 사용한다.

승인 관리 : 검토 중, 승인, 반려 상태 관리

우선순위 관리 : 중요도 설정

1. 요구사항 검토

- 여러 사람이 모여 요구사항 문서를 읽고 문제를 찾는다.
오타, 잘못된 가정, 애매한 표현, 누락, 모순, 표준위반점을 찾는다.
- 검토자 그룹을 어떻게 구성하느냐가 중요하다
예를 들어 고객 중심 프로젝트에서는 검토자 그룹에 고객 대표자가 1명 이상 포함되어야 한다.
- 검토는 시스템 정의서, 시스템 사양서, 소프트웨어 요구사항명세서를 완성한 시점에서 이루어진다.

시스템 정의서

- 무엇을 만드는지 큰 방향을 정의하는 문서(주요 기능만 정의)

시스템 사양서

- 정의서보다 조금 더 구체적인 문서 (그 기능들이 어떻게 동작할 것인지)

소프트웨어 요구사항 명세서

- 개발자가 실제 구현할 수 있을 정도로 상세하게 적은 문서

1. 프로토타이핑(Prototyping)

- 최종 제품을 만들기 전에 일부 기능이나 화면을 미리 만들어 사용자가 확인하도록 하는 방법
- 소프트웨어 요구사항에 대해 소프트웨어 엔지니어가 해석한 것을 확인할 수 있다.
- 처음에는 생각하지 못했던 새로운 요구사항을 도출할 수 있다.

장점

- 분석가의 가정을 파악하고 잘못된 경우 유용한 피드백을 제공한다.
- 사용자 인터페이스의 동적인 행위가 문서나 그래픽 모델보다 프로토타입으로 이해하기 쉽다.
- 요구사항의 가변성이 프로토타이핑 이후에 급격히 감소한다.
- 잘못된 요구사항에 대해 자원 낭비 방지

단점

- 핵심 기능보다 디자인에 집중하게 될 수 있다.
- 프로토타입을 만드는 시간과 비용이 추가로 발생할 수 있다.

프로토타이핑 종류

- 종이에 그림 : 가장 단순함

화면 프로토타입

- Figma와 같은 도구 사용

기능 프로토타입

- 일부 기능을 실제로 구현

모델 검증

- 분석 단계에서 만든 설계 그림이나 문서가 논리적으로 맞는지 확인하는 작업
- 개발 전에 모델 오류를 찾기 위해서 검증을 해야된다.
- 예를 들어 객체 모델의 경우 객체들 사이에 존재하는 의사소통 경로를 검증하기 위해 정적 분석을 수행하는 것이 유용하다.

모델 : 실제 프로그램 코드가 아니라 개발 전에 만드는 분석용 설계 자료

모델의 종류
업무 흐름도 : 사용자가 어떤 순서로 업무를 처리하는지 나타내는 그림
유스케이스 다이어그램 : 사용자가 시스템으로 무엇을 할 수 있는지 나타낸 그림
객체 모델 : 시스템 안에 어떤 객체들이 있고 서로 어떻게 연결되는지 나타낸 모델
클래스 다이어그램 : 클래스, 속성, 메서드, 관계를 표현한 그림
데이터 모델 : 데이터베이스에 어떤 데이터가 저장되는지 나타낸 모델

의사소통 경로

- 객체들끼리 정보를 주고받을 수 있는 연결 관계
예 : 도서 대여 시스템에서 회원이 도서를 빌려면 다음과 같이 동작해야 한다.
회원 -> 대여 -> 도서

회원이 대여를 요청하고, 대여 객체는 도서 객체에게 재고나 대여 가능 여부를 확인해야 한다.
이때 대여와 도서 사이에 연결이 없다면 문제가 생긴다.
회원 -> 대여 도서
이렇게 되어 있으면 대여 객체가 도서 정보를 확인할 길이 없다.
필요한 의사소통 경로가 빠진 상태라고 한다.

정적분석

- 프로그램을 직접 실행하는것이 아닌, 구조만 보고 검사하는 방식
- 객체 모델을 실행할 수는 없지만, 그림이나 관계를 보고 구조적으로 검사하는 것

기술적 위험 분석

- 요구사항을 구현하기 위해 사용할 기술이 문제를 일으킬 가능성이 있는지, 문제가 생겼을 때 영향이 얼마나 큰지 판단

복잡성

- 기술이 너무 복잡하거나 우리 시스템 구조와 맞지 않아 문제가 생길 가능성

검증 여부

- 이 기술이 이미 많이 사용되어 믿고 쓸 수 있는가?

의존성

- 이 기술이나 업체가 없으면 우리 시스템이 계속 운영되기 어려운가?

특정 업체 기술에 의존 -> 업체에 문제가 생기면 -> 우리 서비스에도 문제가 생긴다. -> 의존성 위험 높다

특정 라이브러리만 사용 -> 사용자가 증가돼서 라이선스 비용이 오름 -> 예상 비용 증가 -> 의존성 위험 높다

이해관계자 검증을 거친 타당성 분석 결과를 확인하고 배포 및 공유

1. 이해관계자 검증을 거친 타당성 분석 결과를 의사 결정자가 확인한다.

- 의사 결정자의 확인을 통해 요구사항의 시스템화 타당성 분석 결과에 대한 검증 작업 결과를 공식화 한다.

2. 확정된 타당성 분석 결과를 이해관계자에게 배포하여 공유한다.

- 의사 결정자의 확인으로 공식화된 요구사항의 시스템화 타당성 분석 결과를 관련 이해관계자에게 배포 및 공유함으로써 다음 단계로 진행될 수 있도록 한다.
